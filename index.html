A backend fake that lets the web portal and mobile app be tested in isolation

Situation
A client's device-control platform, with a web portal and a mobile app. Actions in the apps reach real customer hardware, so testing against shared environments was risky, slow to set up and impossible to make fail on demand.
What I did
Built a fake of the whole backend that reuses the backend's own request handling (routing, validation, auth guards), so responses match by design, with every API operation covered and checked against the API contract. Each test login gets its own isolated data from 12 scenarios, with failures, delays and the clock controllable per test. Then built a Playwright suite for the portal on top of it: every user role, exact-request checks, failure-path tests and a known-defects register. The mobile app runs against the same fake.
Result
205 portal tests that run on a laptop and never send a request to a real environment or device, plus 118 tests on the fake itself and 44 on the suite's own logic. Confirmed portal defects stay visible as labelled tests until they're fixed, and a new backend release is absorbed by re-syncing the contract.

Static analysis of the frontend and backend: finding what the UI can't show

Situation
UI tests only see what the screens show. Some of the riskiest defects, like missing authorization checks, silent failures in device commands and unsafe defaults, never surface in the UI. On a platform that controls real hardware, they can't be explored on live environments either.
What I did
Before each group of UI tests, I read the portal's code, mapped every screen to the requests it sends, and listed the defects the code predicted, then confirmed them with tests. On the backend, I reviewed every controller, guard, validation rule, service, migration and CI file line by line (about 16,000 lines and 85 routes), and added strict type checking, a dependency audit, custom static-analysis rules and offline probes of library behaviour. Nothing was ever sent to a real environment or device.
Result
Backend: 43 findings (6 critical, 11 high) traced to a few root causes, each with its impact, a recommended fix and acceptance criteria, plus a phased remediation plan. Portal: 20 defects filed with the team, several first spotted in the code, each confirmed by a test or reviewed with the developers.

From a 214-case test design to an automated pilot gate

Situation
The pilot test design I wrote for the founder (below) had 214 cases, 131 of them pilot blockers, covering roles, data imports, password-protected sponsor reports, transcripts and transcript validation. The pilot could only start once every blocker passed, and that gate had to be re-checked on every release without a QA team to run it by hand.
What I did
Automated it in Playwright against the in-browser demo build, where the real backend and its database run inside the page, so every test gets a freshly seeded world with no server to share. Every test is tied to a case ID, and a custom reporter maps all 214 cases to passed, known defect, staging-only, manual or not yet, so no gap goes without a reason. The protected PDFs and spreadsheets are opened the way a sponsor would open them: with no password, the wrong one and the right one, then read to check field order, labels and marks.
Result
Every pilot blocker is now either automated or has a written reason (8 need the deployed stack or a person), and a full run takes about 14 minutes. The suite found 4 defects, including a crash that took down the dashboard for everyone after one unmapped sponsor code, and a demo-only bug that broke every "remove" action. Each defect stays as a labelled expected failure until it's fixed.

Testing and evidence that held up in PCI DSS, ISO 27001 and SOC 2 audits

Situation
Two regulated FinTech products had formal audits to pass: a payments platform going through PCI DSS Level 1, and a gratuity and savings SaaS working towards ISO 27001 and SOC 2. Auditors don't accept "we tested it". They ask for proof that every change was tested and that the security controls actually work.
What I did

PCI DSS (Easykash): tested that card data was masked across the mobile apps, receipts and logs and never stored or shown in full; verified role-based access and least privilege for admin and merchant users; retested and documented the fixes from vulnerability scans and penetration tests; and made every release carry linked test cases, results and QA sign-off as change-control evidence.

ISO 27001 and SOC 2 (FinFlx): wrote the QA policies the auditors reviewed (test strategy, release process and Definition of Done, defect management), set up traceability in Jira from requirement to test case to result to release, tested the product's security controls (access, audit logging, data handling), and walked the auditors through the process, pulling evidence samples on request.

Result
All three passed: PCI DSS Level 1, ISO 27001 certification and the SOC 2 attestation, with QA's testing and change-control evidence accepted as part of each audit. The same habits (traceable tests, documented sign-off, security checks in every release) carried into how I run QA today.

QA consultant · EdTech startup214 cases · go/no-go gate

Pilot test strategy for a university reporting portal

Situation
A pre-launch UK EdTech startup was heading into its first university pilot. Its product sends scholarship sponsors password-protected progress reports on their students, so one wrong or unprotected report is a serious incident. The founder brought me in to define what "ready for the pilot" means and how to prove it.
What I did
Wrote the pilot test design: 214 cases across 14 areas, 131 marked as pilot blockers, with P1–P3 priority and S1–S4 severity scales and entry and exit criteria. Designed the test data so each of 19 seeded students triggers a specific rule, plus 13 crafted edge-case files (oversized, malformed, Arabic and emoji text), and a staging mock of the student-record systems with fault scenarios.
Result
A clear go/no-go: ready when every P1 passes, at least 95% of P2 pass, no S1 or S2 defect is open, and the end-to-end journey passes twice on a fresh reseed.
